# Cameleer 0.6.1: the HTTP stack on simoom

<!-- GitHub Release body for v0.6.1. The full list of changes is the 0.6.1 section of CHANGELOG.md. -->

Cameleer's HTTP server and HTTP client now run on [simoom](https://crates.io/crates/simoom), the std-only
HTTP engine of the Cameleering family. The server uses an event loop per core instead of a thread per
connection; the client pools connections, multiplexes HTTP/2 and streams bodies. The release also carries
the entry for the official MCP Registry.

**Breaking, in a patch number:** the `http2` cargo feature is gone, response header names are lower case,
and the HTTP clients refuse to turn certificate verification off. Read [Upgrading](#upgrading) before you
pull. (The MCP Registry checks published artifacts, and crates.io never changes a published version, so the
registry entry needed a new version number; this release is that version.)

## What's new

### The HTTP server runs on simoom

- An event loop per core serves plain HTTP and HTTPS (TLS 1.2 and 1.3, client certificates) for
  `platform-http`, `http`, the REST DSL, the MCP endpoint, the dev console and the emulators.
- **A route starts on a pool of threads and moves to the loop** when its handler proves fast: 126 of
  128 calls under 1 ms. It goes back when it stalls the loop. A handler that never blocks (the MCP
  endpoint) answers from any thread through a responder, with no thread waiting.
- Measured on DigitalOcean `c-4` machines, the previous server against this one, same machines and rounds,
  three rounds in all:

  | scenario | requests per second | p99 latency | CPU per request | threads |
  |---|---|---|---|---|
  | `http`, 64 connections | **1.33x** | 2.05 to 0.75 ms | 30 to 16 µs | 67 to 4 |
  | `http`, 256 connections | **1.56x** | 7.06 to 2.67 ms | 31 to 16 µs | 202 to 4 |
  | `rest-json`, 64 | **1.31x** | 2.61 to 1.25 ms | 37 to 20 µs | 67 to 4 |
  | `mcp-session`, 64 | **1.37x** | 5.64 to 3.18 ms | 83 to 46 µs | 147 to 71 |

  Peak memory is about half. The report, the raw data and the two earlier rounds, including the round
  where MCP was slower (0.88x) and why, are in
  [docs/design/simoom-adoption.md](https://github.com/cameleering/cameleer/blob/main/docs/design/simoom-adoption.md).

### The HTTP client runs on simoom-client

- The `http` and `https` producers, `HttpClient` and everything built on it (MCP, SaaS, datastore, FHIR and
  DICOMweb clients) use one shared client per set of settings: HTTP/1.1 keep-alive pooling, HTTP/2
  multiplexing, proxies, redirects and streamed request and response bodies.
- `httpVersion=HTTP/2` works in every build, also with a streamed body.
- The Camel exceptions and messages are unchanged: connection refused, read timeout, TLS certificate errors.
  A plain `http://` request to a TLS port reports "Connection closed unexpectedly: the answer is not HTTP".

### The `cameleer` crate and the MCP Registry entry

- `cargo install cameleer` installs the `cameleer` command and `cargo add cameleer` gives the
  `cameleer-main` API (first published with 0.6.0).
- `server.json`, the `mcp-name` line in the crate README and the image label are the entry for the official
  MCP Registry.

## Upgrading

- **`--features http2` is now an error:** drop it. HTTP/2 is part of every build.
- **Certificate verification cannot be turned off in the HTTP clients.** `hostnameVerification=false`,
  `insecureSkipVerify` and `trustAllCertificates` on the `http` and `https` producers (and on the
  components that use `HttpClient`) are refused with a message that says what to do: trust a private server
  with `trustStore`, or set `serverName` to the name in its certificate. The AWS, Azure and Google Cloud
  components keep their own client and their `trustAllCertificates` for now.
- **Response header names are lower case**, as HTTP allows. Code that compares them case-sensitively
  must compare without case.
- **An HTTP/1.0 client gets an HTTP/1.1 status line.** It still gets a body with a length, never chunked.
- **The server refuses requests that are ambiguous or malformed:** request-smuggling shapes, and `|` and
  other unsafe bytes in the request target. The HTTP client now percent-encodes those bytes like curl and
  Java's client do.
- **`ServerConfig.pool_size`** (Rust API) now limits the threads for routes that block, not connections.
- **Images:** `cameleering/cameleer` on Docker Hub and `ghcr.io/cameleering/cameleer`, as in 0.6.0, with the
  new tags `0.6.1`, `0.6`, `latest`, `0.6.1-health` and `health`.

## Measured

- The tables above are simoom's gain over the previous Cameleer server. They are not a comparison with
  Apache Camel: that comparison is in the 0.6.0 notes and `docs/BENCHMARKS.md`.
- **Binary size:** the `full` build grows 1.7% (25.73 to 26.17 MB, Linux `dist`), the `core` build 7.4%
  (6.01 to 6.45 MB), measured with the old code still in place.
- **Tests:** the hermetic suite (`cargo test --workspace`) passed 2,971 tests with 0 failures on Windows 11
  and passes in CI on Linux and Windows, with zero build warnings.

## Limits

- **Not run for this release:** the live-server, official-client and simulator test tiers, which need
  root in WSL. They matter most for the new client; the hermetic suite is what stands behind it.
- **Still on the old code:** WebSocket, the gRPC server and the HTTP/2 server and client under it, and the
  AWS, Azure and Google Cloud components' HTTP client. They move in later releases.
- **A route that is fast for 126 of 128 calls and then blocks** stalls one event loop until the server moves
  it back to the pool; a route that blocks on a request to its own server can hang a loop for that call.
- **Release archives:** the signed archive workflow runs on the `v0.6.1` tag for the first time. If the
  archives are not attached to this release, use the images or `cargo install cameleer`.
