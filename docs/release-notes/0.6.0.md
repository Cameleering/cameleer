# Cameleer 0.6.0: packs, the health pack, and attestation

<!-- GitHub Release body for v0.6.0. The full list of changes is the 0.6.0 section of CHANGELOG.md. -->

Cameleer 0.6.0 adds **packs**: optional, industry-specific sets of components with their own
version. The first is the **health pack**: HL7 v2, MLLP, FHIR R4, and new DICOM support. Apache
Camel has no DICOM component. This release also serves **existing routes as MCP tools with no
edits** and adds **attestation in confidential VMs**. The project now lives in the GitHub
organization **Cameleering**.

**Breaking:** HL7, MLLP and FHIR left the default build and image. If you use them, read
[Upgrading](#upgrading) before you pull.

## What's new

### The health pack (`cameleer-health` 0.6.0)

- **HL7 v2 and MLLP**: the `mllp` component, the `hl7` data format and the `hl7terser` language.
  These moved from the default build.
- **FHIR R4**: the `fhir` component and the `fhirJson` and `fhirXml` data formats. These also
  moved from the default build.
- **DICOM** (new):
  - **`dicom` component:** DIMSE over TCP and TLS. It works as an SCP and as an SCU for C-ECHO,
    C-STORE, C-FIND, C-MOVE and C-GET.
  - **`dicomweb` component:** STOW-RS, QIDO-RS and WADO-RS, as a client and as a server.
  - **Data formats:** `dicom`, which converts Part 10 files and back, byte for byte, and
    `dicomJson`.
  - **De-identification:** `dicomDeidentify` applies the PS3.15 Annex E basic profile and its
    options. It is deterministic under a key and writes audit records to a hash-chained log.
  - **Expressions:** `${dicom.*}` in Simple, and the `dicom` language.
- **Getting it:** the image `cameleering/cameleer:health`, or `--features health`. The pack costs
  about 2 MB of binary (30.91 MB against 28.99 MB for the Linux `dist` build).
- **DICOM Conformance Statement:** a
  [PS3.2 conformance statement](https://cameleer.ing/docs/packs/health/conformance/dicom-conformance-statement-0.6.0.html).
  Its tables are generated from the code and checked by a test.
- **Pack information at run time:** `cameleer version`, `/q/info` and `/q/dev/packs` show which
  packs a build contains.
- **For Rust users:** packs plug in through `cameleer_core::pack` and `Main::add_pack`.

Guides: [the health pack](https://cameleer.ing/docs/packs/health/),
[DICOM](https://cameleer.ing/docs/packs/health/guides/dicom.html),
[healthcare overview](https://cameleer.ing/healthcare/).

### Existing routes as MCP tools: `--mcp-expose`

`cameleer run orders.camel.yaml --mcp-expose rest:*` serves routes to MCP clients without
changing the route files:

- REST DSL operations become tools, with typed arguments taken from their documented parameters.
- `direct:` routes and `route:<id>` routes take a body and headers.
- GET operations are read-only. Writes need approval by default.
- Every call goes through the tool envelope.
- Overrides per route accept every `ai-tool` option.

See the [MCP server guide](https://cameleer.ing/docs/guides/mcp-server.html#expose-existing-routes-without-editing-them).

### Attestation in confidential VMs (`cameleer-attest`, in the default build)

Set `camel.attestation.enabled=true` inside one of these:

- an Intel TDX guest (Linux configfs-tsm);
- an AMD SEV-SNP guest (Linux configfs-tsm);
- a dstack CVM.

Cameleer then serves hardware evidence at `/q/attestation`. The evidence is bound to:

- the client's nonce;
- the server's TLS key;
- a manifest of the routes, the configuration (without secrets) and the tools;
- a hash-chained log of later changes to them.

MCP clients get the same evidence in the handshake `_meta`. With
`camel.attestation.mcp-tool=true` they can also get it as a tool. Start-up fails if attestation is
on and no evidence can be produced. See the
[attestation guide](https://cameleer.ing/docs/guides/attestation.html) and
[cameleer.ing/trust](https://cameleer.ing/trust/).

### Fixes and behaviour changes

- **One port for HTTPS routes and the management endpoints:** with
  `camel.server.sslEnabled=true`, HTTPS routes, `/q/*`, `/q/attestation` and MCP share one port.
  Before, start-up failed. Camel's separate management port (`camel.management.*`) is supported too.
- **Changed: `onException` and `doCatch` for `Exception` now catch `CamelExchangeException` and
  the kinds under it**, such as `HttpOperationFailedException` and `ValidationException`. They
  were missed because the exception was listed as its own parent. This matches Camel. A route
  whose `Exception` handler used to let these failures through now handles them.
- **Changed: route configurations apply whatever the file order.** Top-level `onException`,
  `intercept` and `interceptSendToEndpoint`, and a `routeConfiguration` without id, now apply to
  every YAML route. Before, they applied only to routes in files loaded after them.
- **`cameleer validate` checks `routeConfigurationId` across files:** a configuration in a later
  file is accepted, and an unknown id is an error.
- **`/q/metrics`** sends one `Content-Type` header.
- **Readiness:** a suspended consumer is reported as `DOWN` in the details too.

### Distribution

- **Release archives:** `cameleer-0.6.0-<target>` and `cameleer-health-0.6.0-<target>`, each
  with a SHA-256 checksum and a CycloneDX SBOM of exactly what the build compiles in.
- **Signatures:** on release tags the archives, checksums and SBOMs are signed with keyless
  Sigstore cosign.
- **Images:** a health variant is built next to the general image.

## Upgrading

- **Images moved.** Pull `cameleering/cameleer` (Docker Hub) or `ghcr.io/cameleering/cameleer`.
  - Tags: `latest`, `0.6.0`, `0.6`, `health`, `0.6.0-health`, `0.6-health`, and `edge` for manual
    builds.
  - **The old paths `pmsudhi/cameleer` and `ghcr.io/pmsudhi/cameleer` stop at 0.5.1 and get no
    new tags.** Update your Dockerfiles, Compose files, Helm values and Kubernetes manifests.
- **HL7, MLLP or FHIR users:** switch to one of these:
  - `cameleering/cameleer:health`;
  - `cargo install cameleer-main --features health`;
  - for a smaller build, `--no-default-features --features health` plus the families you need.

  A route that uses one of these components in a build without the pack fails at start, and the
  message names the pack, the image and the feature.
- **Rust users of the moved modules:** there are no aliases.

  | before | now |
  |---|---|
  | `cameleer_protocols::{hl7, mllp}` | `cameleer_health::hl7::{self, mllp}` |
  | `cameleer_soap::fhir` | `cameleer_health::fhir` |
  | socket helpers in `cameleer-protocols` | `cameleer_tls::net` |
  | SOAP producer client | `cameleer_http::client::EndpointClient` |
  | `now_utc` | `cameleer_core::util_time::now_utc` |
- **Exception handling:** check routes that rely on `onException(Exception)` *not* catching HTTP,
  validation or endpoint-resolution failures. Those failures are now caught.
- **Route configurations in multi-file projects:** a configuration now also applies to routes
  in files loaded before it.
- **Source:** the repository is
  [github.com/cameleering/cameleer](https://github.com/cameleering/cameleer). The old GitHub URLs
  redirect, but update your git remotes.

## Measured

- **MCP tool calls:** the comparison was rerun on 2026-11-12, all sides in one session, on
  DigitalOcean c-4 machines:

  | | Cameleer | Apache Camel `camel-mcp-server` | official TypeScript SDK |
  |---|---:|---:|---:|
  | session tool calls per second | 39,922 | 22,604 | 2,257 |
  | memory | 56 MB | 289 MB | 197 MB |

  - Cameleer handles 1.77x Camel's tool calls per second and 17.7x the SDK's.
  - **Camel's p99 latency is lower: 5.2 ms against 6.3 ms.**
  - The SDK figure is higher than in 0.5.0 because the baseline moved to zod 4.

  The report and the raw data are in [docs/BENCHMARKS.md](https://cameleer.ing/docs/BENCHMARKS.html).
- **Health pack, live tier:** `CAMEL_HEALTH_INTEROP=1` passed 10 of 10 against these servers:
  - DCMTK 3.6.7, in both roles, with and without TLS;
  - Orthanc 1.12.2 with DICOMweb 1.16;
  - python-hl7 0.4.5, as an MLLP receiver and as a client;
  - the HAPI FHIR JPA server 8.12.0.
- **DICOM files:** 33 public pydicom test files are read and written back byte for byte.
- **Tests:** the hermetic suite (`cargo test --workspace`) passed 2960 tests with 0 failures on
  Windows 11 when the health pack was merged, with zero build warnings.

## Limits

- **Attestation hardware:** attestation has not yet run on real TEE hardware. The tests use a
  simulated configfs-tsm directory and a simulated dstack agent.
- **Attestation verification:** Cameleer produces the evidence and the binding but does not verify
  Intel's or AMD's signature chain itself. A platform verifier, such as Intel Trust Authority,
  Microsoft Azure Attestation or dstack's verifier, does that.
- **Health pack, not tested:** cloud DICOM services (Azure, Google, AWS), dcm4che and real
  modalities.
- **Health pack, not built:** pixel codecs (JPEG, JPEG-LS, JPEG 2000, RLE), Storage Commitment,
  MPPS, and IHE ATNA audit messages. There is no visual channel editor and no importer for Mirth
  channels.
- **New workflows:** the archive workflow and the health image build run for the first time with
  this release. `scripts/package-archive.sh` was run end to end on Linux beforehand.
