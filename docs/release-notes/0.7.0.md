# Cameleer 0.7.0: gRPC and HTTP/2 on simoom, certificates always verified

<!-- GitHub Release body for v0.7.0. The full list of changes is the 0.7.0 section of CHANGELOG.md. -->

0.6.1 moved the HTTP server and client onto [simoom](https://crates.io/crates/simoom), the std-only HTTP
engine of the Cameleering family. 0.7.0 finishes the move: the gRPC client and server and everything that
spoke HTTP/2 now run on it too, and the old HTTP/2 and HPACK code is deleted. Two things follow for users:
the HTTP server speaks HTTP/2, and no Cameleer client can be told to skip certificate verification any more.

This release has **behaviour changes** (listed under [Upgrading](#upgrading)); read them before you pull.

## What's new

### The gRPC client and server run on simoom

- The `grpc` producer, the Pub/Sub streaming pull and Pub/Sub Lite clients and the Kinesis
  `SubscribeToShard` stream use simoom-client: one HTTP/2 connection per channel, shared by concurrent
  calls, connected on first use and again after it closes.
- The `grpc` consumer and the cloud emulators use a simoom server: an event loop per core, h2c prior
  knowledge, `Upgrade: h2c` and TLS with ALPN `h2`. A call starts when its first request bytes arrive, so a
  bidirectional stream is answered while the client is still sending. A call that ends without a message is
  answered trailers-only, and a panicking handler becomes `INTERNAL` instead of a dead stream.
- Found on the way: a cancel from another thread did not wake a `recv` that was already waiting, which hung
  the Pub/Sub streaming consumer. The client now waits in short slices and watches a cancel flag; a test
  covers it.
- The own HTTP/2 and HPACK implementation of `cameleer-grpc` (about 3,900 lines with its tests) and the
  HTTP/1.1 reader and writer left in `cameleer-http` (about 700 lines) are gone. `cameleer_grpc::h2` keeps only
  `H2Config`.

### The HTTP server speaks HTTP/2

- `platform-http`, `jetty`, `undertow`, `netty-http`, `rest` and the MCP endpoint serve HTTP/2 next to
  HTTP/1.1: h2c prior knowledge and `Upgrade: h2c` on plain HTTP, ALPN `h2` on HTTPS. Routes need no change.
- Go's HTTP/2 client talks to the server (1 MiB upload across flow-control windows, 16 concurrent streams),
  and Go's client negotiates `HTTP/2.0` with a `jetty:https` route.

### Certificates are always verified

- The gRPC client refuses `insecure_skip_verify`; the AWS, Azure and Google components refuse
  `trustAllCertificates=true` and a global `camel.ssl.trustAllCertificates` when the endpoint is created. The
  message says what to do.
- The cloud components take `sslContextParameters=#bean` and the global `camel.ssl.*` settings, so a
  private CA or a local emulator's certificate is trusted through a trust store:

  ```properties
  camel.ssl.enabled=true
  camel.ssl.trustStore=ca.crt
  ```

## Upgrading

- **`trustAllCertificates=true` on `aws2-*`, `azure-*` and `google-*` endpoints now fails** when the
  endpoint is created. Trust the server's certificate or CA instead (`sslContextParameters=#bean`, or
  `camel.ssl.trustStore`). The cloud HTTP client has no insecure mode any more.
- **The gRPC client always verifies the server certificate and its host name** against the trust anchors it
  is given.
- **An HTTPS consumer negotiates `h2`** with clients that offer it; before, it answered HTTP/1.1 only. A
  client that does not offer `h2` still gets HTTP/1.1.
- **The gRPC server's flow-control windows and frame size are simoom's own.** `flowControlWindow` and the
  frame settings of `H2Config` apply to the client side only; `maxConcurrentCallsPerConnection` and the
  header limits still apply to the server.
- **A plain HTTP/1.1 request to a gRPC port gets a 4xx** instead of 505.
- **Rust API:** `H2Server`, `H2Connection`, the frame types and the `hpack` module of `cameleer-grpc` are
  gone, and so are the HTTP/1.1 reader and writer functions in `cameleer_http::http` (`read_request`,
  `write_response` and the others). Use simoom and simoom-client, or the producers and consumers.
- **Images:** `cameleering/cameleer` on Docker Hub and `ghcr.io/cameleering/cameleer`, with the tags
  `0.7.0`, `0.7`, `latest`, `0.7.0-health` and `health`.

## Measured

- **Tests:** the hermetic suite (`cargo test --workspace`) passed 2,961 tests with 0 failures on Windows 11
  and passes in CI on Linux and Windows, with zero build warnings.
- **Official clients (Linux, Go 1.24.7 and grpcio):** Go's HTTP/2 against the server and the server's HTTPS
  consumer, Cameleer's HTTP/2 client against a Go server, the TLS client and server against Go's
  `crypto/tls`, and the gRPC producer and consumer against grpcio all pass.
- **Not measured for this release:** throughput, latency and binary size of the gRPC and HTTP/2 paths. The
  numbers in the 0.6.1 notes are for the HTTP/1.1 server and client.

## Limits

- **Not run for this release:** the live-server and simulator test tiers, and the `gcloud` CLI check of the
  official tier (it needs the Google Cloud SDK).
- **Still on the old code:** WebSocket, and the HTTP client of the AWS, Azure and Google components (their
  own HTTP/1.1 client over `cameleer-tls`).
- **A gRPC call starts with its first request bytes,** not with the request headers: a client that opens a
  stream and waits for the server to speak first, without sending anything, is not answered until it sends.
- **The cloud HTTP client is HTTP/1.1 only.**
