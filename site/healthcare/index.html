Healthcare integration · the health pack

An open-source healthcare integration engine: HL7, FHIR and DICOM in one binary

Receive HL7 v2 over MLLP and acknowledge after delivery, talk to FHIR servers, route medical images over DIMSE and DICOMweb, and de-identify them with the PS3.15 profile. Every interface is an Apache Camel YAML route kept in Git and tested in CI, run by one native binary that fits on a hospital gateway. Apache-2.0, no licence fees, no lock-in.

Status: the health pack ships with the next release, as the image pmsudhi/cameleer:health and the cargo feature health. HL7, MLLP and FHIR are in the default image up to 0.5.1; DICOM is new. What it does not do yet.

What is in the pack

HL7 v2mllp, the hl7 data format, the hl7terser languagereceive and send ADT, ORM, ORU and other messages over MLLP with automatic AA, AE or AR acknowledgements; read fields by path (PID-3-1); parse ER7 into a structured value and back; TLS

DICOMdicom, dicomweb, the dicom and dicomJson formats, the dicom language and ${dicom.*}C-ECHO, C-STORE, C-FIND, C-MOVE and C-GET as SCU and SCP; STOW-RS, QIDO-RS and WADO-RS as client and server; route and edit on tags; DICOM JSON for indexing

Plus everything else in Cameleer: Kafka, AMQP, databases, files and SFTP, HTTP and REST, cloud services, Apache Camel's routing and error-handling patterns, and MCP tools for AI agents. The DICOM Conformance Statement (PS3.2 form) lists every DICOM service and policy.

What healthcare teams build with it

HL7 to the EHR

ADT and lab messages in over MLLP, the patient id read with a terser path, posted to the EHR, and acknowledged only after delivery, so the sender resends on failure.

An imaging gateway

Modality to PACS or a cloud DICOMweb store over DIMSE and STOW-RS, filtered on tags, with store-and-forward when the uplink is down.

AI inference routing

De-identify the series a model needs, send it to the inference service, and post the finding back as a FHIR DiagnosticReport that points at the original study.

De-identification for research

A folder in, a folder out: pseudonyms that stay consistent across batches and sites, shifted dates, and an audit record per instance.

HL7 v2 to FHIR

Read segments with the terser, build the resource, post it with the fhir producer, and drop duplicates on the message control id.

Provable processing

Get it

Docker

docker run --rm -p 2575:2575 -v "$PWD:/routes:ro" \
  pmsudhi/cameleer:health run /routes/adt.camel.yaml

The :health image (also :<version>-health and on ghcr.io) comes with the next release.

Cargo, or your own Rust program

cargo install cameleer-main --features health

A Rust program depends on cameleer-health and calls ctx.add_pack(&cameleer_health::HEALTH). Release archives come with SHA-256 sums, a CycloneDX SBOM and a Sigstore signature: verify a download.

- route:
    id: adt-to-fhir
    from:
      uri: "mllp://0.0.0.0:{{env:MLLP_PORT:2575}}"
      steps:
        - setHeader:
            name: PatientId
            hl7terser: PID-3-1
        - log: "ADT ${header.CamelMllpTriggerEvent} for patient ${header.PatientId}"
        - to: "log:adt"

Coming from Mirth Connect or another interface engine?

The full comparison, with the open-source forks, the commercial engines and sources for every fact: Mirth Connect alternatives.

Why teams look at Cameleer

  • Apache-2.0 open source. Mirth Connect moved to a commercial licence from version 4.6.
  • Interfaces as code: YAML routes in Git, reviewed and tested in CI with cameleer validate and cameleer test.
  • One small native binary instead of a JVM and a database: starts in milliseconds and runs on a gateway.
  • HL7, FHIR and DICOM in the same engine as Kafka, databases, cloud services and AI tools.

What it does not have

  • No visual channel editor and no message browser.
  • No importer for Mirth channels, and Mirth's JavaScript transformers do not run; transformations are Camel steps (Simple, jq, terser paths).
  • Not tested against dcm4che or real modalities yet.

What it does not do yet

  • Not a PACS, a viewer or an EHR. It moves, transforms and de-identifies data between them.
  • Cloud healthcare services not tested yet: Azure Health Data Services, the Google Cloud Healthcare API, AWS HealthImaging (which also needs SigV4 signing).
  • DICOM not supported yet: Storage Commitment, MPPS, UPS-RS, WADO frames and rendered images, transcoding compressed pixel data and the pixel de-identification options.
  • Audit format: hash-chained records, not yet IHE ATNA messages.
  • No throughput numbers yet against Mirth, dcm4che, DCMTK or Orthanc.
  • Compliance: Cameleer provides controls (TLS, de-identification, audit, attestation); it is not HIPAA certified or FDA cleared.

Common questions

Is there an open-source healthcare integration engine for HL7, FHIR and DICOM?

Cameleer's health pack is one, under the Apache-2.0 licence: HL7 v2 over MLLP with acknowledgements, the hl7 data format and terser paths, the fhir component and FHIR JSON and XML, DICOM over DIMSE and DICOMweb, and PS3.15 de-identification. Integrations are Apache Camel YAML routes run by one native binary.

Is Cameleer an alternative to Mirth Connect?

For teams that keep integrations as code, yes: channels become routes in YAML files kept in Git, tested in CI, with Apache Camel's error handling and routing patterns, under the Apache-2.0 licence. It has no visual channel editor, no message browser and no importer for Mirth channels, and it does not run Mirth's JavaScript transformers.

Which image or build has the healthcare components?

The health pack, from the next release: the image pmsudhi/cameleer:health, or cargo install cameleer-main --features health. The default image and the full build do not include it. Up to 0.5.1, mllp, hl7 and fhir are in the default image; DICOM is new in the pack.

How was it tested?

The health pack's live tests pass 10 of 10 against DCMTK 3.6.7, Orthanc 1.12.2 with its DICOMweb plugin, python-hl7 0.4.5 (MLLP both ways, AA and AR acknowledgements) and the HAPI FHIR 8.12.0 server (create, read, update, search, history, delete, JSON and XML). 33 public pydicom test files are read and written back byte for byte.

Is Cameleer HIPAA compliant?

Compliance belongs to a deployment, not to a library. Cameleer gives you controls: TLS and mutual TLS on MLLP, DIMSE and HTTP, PS3.15 de-identification with audit records, a hash-chained audit log, and, from the next release, attestation in a confidential VM. It is not certified, cleared or audited for HIPAA or by the FDA.

Can I ask for a feature the health pack does not have?

Yes. Open a feature request on GitHub with your workflow, the systems involved and what you use today. Requests are read and answered on the issue, and worked on with the person who asked.
