Apache Camel's MCP server vs Cameleer

Apache Camel 4.22 added camel-ai-tool and camel-mcp-server: routes become tools that MCP clients can call. Cameleer implements the same option and property names, so the routes and the configuration look the same. The difference is what happens around each call, and the runtime the server runs on. The overview, environments and tested use cases are on the Cameleer MCP page.

What stays the same

A tool route and its server configuration read the same on both runtimes.

- route:
    from:
      uri: ai-tool:lookup_order
      parameters:
        description: Look up an order by id
        tags: support
        parameter.orderId: string
        parameter.orderId.required: true
        readOnlyHint: true
      steps:
        - setBody:
            simple: '{"orderId": "${header.orderId}", "status": "shipped"}'
camel.server.mcp-enabled=true
camel.server.mcp-tags=support
  • Tool definition: description, title, tags, parameter.NAME with .description, .required and .enum, argSchema, outputSchema, the four *Hint options, returnDirect, authorizationPolicy.
  • Call semantics: arguments arrive as headers, camel* and undeclared arguments are dropped, the tool runs on a copy that keeps only properties and variables, an empty body is "No result", CamelAiToolCallId and CamelAiToolConversationId.
  • Server behavior: camel.server.mcp-tags=* does not expose untagged items, the server name defaults to the context's name, and route exceptions reach clients as a generic message with an error id unless camel.server.mcp-expose-errors=true.

Also in Cameleer's MCP server

These are documented for Cameleer. Camel may offer some of them too; compare with its documentation.

Protocol

  • Both eras on one endpoint: 2026-07-28 (stateless, server/discover, subscriptions/listen, caching hints) and 2025-11-25, 2025-06-18 and 2025-03-26 (sessions, GET event stream).
  • Streamable HTTP and stdio: cameleer run x.camel.yaml --mcp or --mcp-stdio.
  • Approvals as an input_required result with a requestState sealed with AES-256-GCM (2026-07-28), or as elicitation/create (legacy sessions).
  • Progress, log notifications, elicitation and sampling from inside a tool route.
  • The official conformance suite 0.1.16: 39 of 39 scenarios for 2025-11-25, 26 of 26 for 2025-06-18.

Security and operations

  • API keys, JWTs (JWKS or HMAC) and RFC 7662 introspection; RFC 9728 metadata and RFC 8707 audience checks; an Origin check.
  • The client's token never reaches routes or downstream systems.
  • Guardrails on results: redact (secrets, e-mail addresses, Luhn-checked card numbers, IBANs, custom patterns), authorize predicates, cacheTtl.
  • cameleer tool list, disable, enable, approvals, approve, deny against a running integration.

When to choose which

Apache Camel

  • The tools call Java libraries, beans or an existing Spring Boot or Quarkus application.
  • You need a component Cameleer does not have.
  • Your team already runs Camel on the JVM and the reliability patterns are built into its routes.
  • You need commercial support.

Cameleer

  • Tools change money, orders or records, and retries, approvals and audit must hold for every call, not only in routes that remember them.
  • The server is started by the client over stdio, runs on a laptop or scales to zero.
  • You want one gateway in front of third-party MCP servers, with your rules on their tools.
  • Clients speak different protocol versions.

Common questions

Do my Camel ai-tool routes and MCP properties carry over?

The ai-tool options (description, tags, parameter.*, argSchema, outputSchema, the four hints, returnDirect) and the camel.server.mcp-* properties use Camel's names and semantics, so YAML tool routes and their properties carry over. Java beans do not: an authorizationPolicy, for example, is a Rust implementation of ToolAuthorizationPolicy in Cameleer.

Is Camel's MCP server unreliable?

No. In Camel the tool hints are advisory and the reliability is yours to build in the route with Camel's EIPs: idempotent consumer, saga, throttle, circuit breaker. Cameleer makes those checks part of every call, so a tool cannot forget them.

When should I stay on Apache Camel?

When the tools call Java libraries or beans, when you need a component Cameleer does not have, when the MCP server should live inside a Spring Boot or Quarkus application, or when you need commercial support.

Are there benchmarks of the MCP server?

Yes. On three identical cloud machines (4 dedicated vCPUs each, 64 client connections), Cameleer served 39,922 MCP tool calls per second in sessions against 22,604 for Apache Camel's camel-mcp-server on the JVM and 2,257 for a server written on the official TypeScript SDK, with 56 MB of memory against 289 MB and 197 MB. Stateless 2026-07-28 calls reached 50,514 per second in 26 MB. Every Cameleer call went through the full tool envelope.
