Articles: efficiency, outages and cost, with sources

Essays on why software needs as much as it does, what that costs, and how to measure it. Every external fact is cited; every number of ours names its project and its baseline. New articles also arrive in the Atom feed.

  1. How to test your headroom before an incident: the degraded-fleet test 2026-11-13

    A procedure for a staging fleet: lose a third of the servers, restart one under load, reconnect every client at once, offer more than the fleet can serve. What to record, how to read it, and the pass or fail lines to write first.

  2. Headroom: what is left when servers drop out 2026-11-13

    The Microsoft 365 outage of 12-13 November 2026 was the same traffic on fewer servers. How much a fleet survives losing part of itself is an efficiency property, and it can be measured before an incident.

  3. Code efficiency as a FinOps lever 2026-11-12

    Measured milliseconds and megabytes turned into instances and dollars: Lambda execution time, memory and cold starts, node density, Fargate, with the arithmetic shown.

  4. When a rewrite pays off: a decision checklist 2026-11-12

    The case against rewrites, the ones that worked with published results, the ladder from a setting to a full rewrite, and a checklist.

  5. AI-generated code and performance: what the evidence says 2026-11-12

    Generated code ran 3.12 times as long in one benchmark: what EffiBench, Mercury, EvalPerf, PIE, METR and DORA measured, each with its limits.

  6. Wirth's law in 2026: measured 2026-11-12

    Software growth against hardware speed since 1995: page weight, input latency, single-core speed, and the counter-argument.
