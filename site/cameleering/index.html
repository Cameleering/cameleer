Cameleering · a way of engineering

Carry more on less.

Cameleering is the practice of making software carry the same load on less: less time, memory, size and dependencies. Every gain is proven against the original, on the same hardware, with the method published. Sometimes the answer is a setting or a smaller default. Sometimes it is a rewrite.

Why cameleering, and why now

Cheap hardware, and what we spent it on

Chips got faster every year, and memory and disks got cheaper. That was good news, and we spent it: on features, frameworks and layers, often for good reasons. The cost did not go away. It moved into bigger binaries, slower starts, and machines that sit half idle while they wait.

Along the way the unit of care changed. Engineers who once counted CPU cycles began counting milliseconds, then seconds. Asynchronous calls and loading screens made waiting feel shorter. They did not make it shorter: a spinner hides a bottleneck, it does not remove it.

Coding agents, and more data

Code is now cheap to produce, and the speed of building software has become the benchmark instead of the speed of the software. In one benchmark, code written by GPT-4 took on average 3.12 times as long to run as human solutions to the same tasks [3]. In a 2025 controlled study, experienced developers using AI tools were 19% slower while believing they were faster [4]; a 2026 follow-up suggests that has since changed, but could not measure it cleanly. Either way, those studies measure how fast people finish, not how fast the software runs (the evidence in full). Code duplication in large codebases rose sharply in 2024 [5], though that study cannot say which lines AI wrote, and other research found small quality gains from AI adoption [6].

At the same time every product collects more data than the last, so the work of storing and processing it keeps growing.

Using less is a responsibility

Software runs on someone's machines, someone's time and someone's power. Making it carry the same load on less is part of doing the job well, the same way an engineer is responsible for correctness and security.

To the people who pay for the machines

Every idle gigabyte and every extra instance is paid for, every month, by someone. Software that needs a tenth of the memory needs fewer, smaller machines.

To the people who wait

A second at startup or a slow tail at p99 is a person waiting, or a function billed while it warms up. Real waiting is what users feel, whatever the loader shows.

To the power we all share

The IEA projects data-centre electricity use to roughly double by 2030, to about 945 TWh [2]. One project cannot change that. Every team that measures and removes waste in its own software does its share.

This is about waste, not about the people who build features: features are why software matters. Cameleering reports resources (milliseconds, megabytes, CPU) and makes no carbon claims of its own.

Eight principles

1. Measure before you claim

A number and its method beat any adjective. Targets are labelled as targets until they are measured.

2. Baselines over boasts

Compare against the version people use today, on the same machine, with the exact versions named, and publish both sides.

3. Same job, same contract

Keep the names, options and behaviour people rely on, so the gain costs them nothing to adopt.

4. Pack only what the journey needs

Every feature, dependency and idle thread pays its way in bytes and milliseconds, or it ships as an option.

5. Real waiting over felt waiting

A loader changes how a wait feels. Only engineering changes how long it is.

6. Budgets in the build

Size, memory, startup and latency budgets live in CI, so a regression fails the build instead of reaching users.

7. Rewrite when the numbers say so

A rewrite is a tool, not a creed. Profile and fix first; rewrite when measurement shows the current design cannot get there.

8. Publish the losses

Say where you are slower. A ledger with no red rows is not trusted.

The cameleering process

Seven steps any team can run on its own software, with or without our projects.

stepwhat you do
1. PickChoose software that many people run and that costs a lot to run.
2. BaselineMeasure it on fixed hardware: startup, idle and peak memory, throughput, p99, binary or image size, dependency count. Publish the harness.
3. BudgetSet targets, and label them as targets.
4. CutProfile, remove, simplify, and rewrite only where the design is the limit. Compatibility tests guard the contract.
5. ProveRerun the same harness on the same hardware. Record the losses too.
6. PublishAdd a row to a ledger, with the method and the raw data.
7. GuardTurn the budgets into CI checks and rerun the benchmarks every release.

Cameleer, the first Cameleering project

Cameleer runs Apache Camel's routes, patterns and endpoint URIs unchanged as one native binary, with about 230 components and no third-party dependencies. The cameleer drives the caravan: the project gave the practice its name.

Where it fits

  • At the edge: MQTT, syslog and, with the health pack, HL7 over MLLP on a gateway. Edge gateways
  • In serverless functions: its own AWS Lambda runtime. Serverless
  • Behind AI agents: routes as MCP tools, validated, run once and audited. Cameleer MCP
  • Next to the services you already run: tens of megabytes per integration instead of hundreds. All use cases

How the principles show up in it

  • Same contract: Camel's YAML and XML routes run unchanged.
  • Pack only what the journey needs: cargo features cut the binary to about 6 MB with the core alone.
  • Publish the losses: the p99 loss above, and plain HTTP at 68% of a do-nothing server on the same machines (the HTTP ceiling).
  • Baselines over boasts: compared with Apache Camel on the JVM and on Quarkus native (30 ms startup). Every scenario

Where cameleering comes from, and how it differs

The idea is not new. In 1995 Niklaus Wirth wrote "A Plea for Lean Software", observing that software was growing faster than the hardware that ran it [1]. Cameleering adds a practice: shipped rewrites of widely used software, measured against the original in public.

Common questions

What is cameleering?

Cameleering is the practice of making software carry the same load on less (less time, memory, size and dependencies) and proving every gain against the original, on the same hardware, with the method published. Its one hard rule is no claim without a number.

Does cameleering mean rewriting everything in Rust?

No. A rewrite is a tool, used when measurement shows the current design cannot reach the target. Many gains come from settings, smaller defaults and removed layers (when a rewrite pays off). The projects in the ledger are rewrites in Rust, but the claim is always the measured result, not the language.

What is the difference between Cameleer and Cameleering?

Cameleering is the practice and the organization. Cameleer is one product: an integration engine in the style of Apache Camel, and the first Cameleering project. Other projects carry the line "A Cameleering project".

How is cameleering different from green software or FinOps?

Green software standards such as the Software Carbon Intensity specification measure and report carbon, and FinOps manages cloud spend, mostly at the infrastructure level. Cameleering changes the software itself so it needs fewer resources, and publishes the before and after. The approaches fit together.

How do I start cameleering my own software?

Pick one service, measure it on fixed hardware (startup, idle and peak memory, throughput, p99, size, dependencies), set budgets, remove what does not earn its place, measure again, and publish both numbers. The method page has the checklist and the report format.

Which projects are part of Cameleering?

Cameleer (integration engine, measured), simoom (HTTP server engine, in progress, not measured), karez (database connectivity, design stage, targets only) and ksar (cryptographic primitives and PKI, planned). The ledger shows each one's status.

Where does the name come from?

A cameleer drives a caravan of camels, animals known for carrying heavy loads a long way on little water. Cameleer was the first project; the practice took its name. The projects are named after desert and caravan words, such as simoom (a desert wind) and karez (an underground water channel).

Is Cameleering affiliated with the Apache Software Foundation?

No. Cameleering and Cameleer are independent open-source projects under the Apache License 2.0. Cameleer follows Apache Camel's names and semantics but contains no Camel source code and is not affiliated with or endorsed by the ASF.
