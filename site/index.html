Cameleering

Carry more on less.

Software efficiency, measured against the original.

Cameleering is the practice of making software carry the same load on less (less time, memory, size and dependencies) and proving every gain against the original, on the same hardware, with the method published.

No claim without a number.

The practice is seven steps any team can run on its own software. Here they are as Cameleer ran them against Apache Camel, each with its evidence.

The projects, as proof

To show the method works on ordinary, widely used software, we rewrite some of it and measure the results. A project gets numbers only once it is measured.

Cameleer measured

Integration engine in the style of Apache Camel: its routes, patterns and endpoint URIs as one native binary, with MCP tools for AI agents. Starts in 3 ms where Apache Camel on Java 21 takes 1.1 s.

simoom measured

Embeddable HTTP/1.1, HTTP/2 and HTTP/3 server engine in std-only Rust, no tokio. First of 21 servers on start-up; 43% behind H2O on HTTP/3.

karez and ksar

Database connectivity (design) and cryptography with PKI (planned). No numbers until they are measured.

Why now: using less is a responsibility

Chips got faster and memory got cheaper, and we spent the gain on features, frameworks and layers, often for good reasons. The cost moved into bigger binaries, slower starts and machines that sit half idle. Now code is cheap to produce: in one benchmark, code written by GPT-4 took on average 3.12 times as long to run as human solutions [3], and the studies of AI tools measure how fast people finish, not how fast the software runs (the evidence).

To the people who pay for the machines

Every idle gigabyte and every extra instance is paid for, every month, by someone. Software that needs a tenth of the memory needs fewer, smaller machines.

To the people who wait

A second at startup or a slow tail at p99 is a person waiting, or a function billed while it warms up. A spinner hides a bottleneck; it does not remove it.

To the power we all share

The IEA projects data-centre electricity use to roughly double by 2030, to about 945 TWh [2]. One project cannot change that. Every team that measures and removes waste in its own software does its share.

This is about waste, not about the people who build features: features are why software matters. Cameleering reports resources (milliseconds, megabytes, CPU) and makes no carbon claims of its own.

Eight principles

  1. Measure before you claim. Targets are labelled as targets until they are measured.
  2. Baselines over boasts. The version people run today, on the same machine, with both sides published.
  3. Same job, same contract. Keep the names, options and behaviour people rely on.
  4. Pack only what the journey needs. Every feature, dependency and idle thread pays its way, or ships as an option.
  5. Real waiting over felt waiting. A loader changes how a wait feels; only engineering changes how long it is.
  6. Budgets in the build. Size, memory, startup and latency regressions fail CI.
  7. Rewrite when the numbers say so. A rewrite is a tool, not a creed (when it pays off).
  8. Publish the losses. A ledger with no red rows is not trusted.

Where it comes from, and how it differs

In 1995 Niklaus Wirth wrote "A Plea for Lean Software", observing that software was growing faster than the hardware that ran it [1]. Cameleering adds a practice: shipped rewrites of widely used software, measured against the original in public.

Common questions

What is cameleering?

Cameleering is the practice of making software carry the same load on less (less time, memory, size and dependencies) and proving every gain against the original, on the same hardware, with the method published. Its one hard rule is no claim without a number.

What is the difference between Cameleer and Cameleering?

Cameleering is the practice and the organization. Cameleer is one product: an integration engine in the style of Apache Camel, and the first Cameleering project. simoom, an HTTP engine, is the second.

Does cameleering mean rewriting everything in Rust?

No. A rewrite is a tool, used when measurement shows the current design cannot reach the target. Many gains come from settings, smaller defaults and removed layers. The projects in the ledger are rewrites in Rust, but the claim is always the measured result, not the language.

How is cameleering different from green software or FinOps?

Green software standards such as the Software Carbon Intensity specification measure and report carbon, and FinOps manages cloud spend, mostly at the infrastructure level. Cameleering changes the software itself so it needs fewer resources, and publishes the before and after. The approaches fit together.

How do I start cameleering my own software?

Pick one service, measure it on fixed hardware (startup, idle and peak memory, throughput, p99, size, dependencies), set budgets, remove what does not earn its place, measure again, and publish both numbers. The method has the checklist and the report format.

Does Cameleering sell anything?

No. The projects are open source under the Apache License 2.0, with no paid edition. The maintainer is open to consulting on measuring and slimming software; the about page says how to get in touch.

Is Cameleering affiliated with the Apache Software Foundation?

No. Cameleering and Cameleer are independent open-source projects. Cameleer follows Apache Camel's names and semantics but contains no Camel source code and is not affiliated with or endorsed by the ASF.
