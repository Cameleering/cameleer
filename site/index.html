Cameleering: Camel routes, driven without the JVM.

Cameleering is running Apache Camel integration routes on Cameleer: the same patterns, endpoint URIs and YAML, executed by one native Rust binary that starts in 3 ms and runs in megabytes. It takes Camel-style integration where a JVM does not fit.

  • At the edgeMQTT, syslog and HL7 routing on gateways and small devices, buffering when the uplink is down; arm64 image.
  • In serverless functionsIts own AWS Lambda runtime; the same route on Cloud Run and Knative, with no JVM cold start.
  • Behind AI agentsRoutes as MCP tools that are validated, run once, approved when risky and audited.

What is cameleering?

Keep your routes. Change the runtime.

The same YAML runs on Apache Camel and on Cameleer. Switch the runtime and watch what changes, including Apache Camel compiled natively with Quarkus.

triage.camel.yaml
- route:
    id: triage
    from:
      uri: kafka:support-tickets
      steps:
        - to: "openai:chat-completion?model=gpt-4o-mini"
        - choice:
            when:
              - simple: "${body} contains 'URGENT'"
                steps:
                  - to: kafka:tickets-urgent
            otherwise:
              steps:
                - to: kafka:tickets-routine

The action layer for AI agents.

    
The model decides what; a tested route decides how. Cameleer feeds events to models, routes on their answers, and turns an agent's tool calls into actions that are validated, run once, retried, rolled back and audited.

    
    
      
  1. Events inKafka, MQTT, webhooks, files, mailboxes, queues, databases
    2. 
      
  2. Model23 providers: OpenAI, Anthropic, Gemini, Bedrock, Azure OpenAI, Vertex AI, Ollama and OpenAI-compatible services, with retries, fallbacks and caching in process
    3. 
      
  3. Route on the answercontent-based routing on a fixed label set, JSON schema checks on the output, a re-ask on failure
    4. 
      
  4. Reliable actionsMCP or REST tools with schema validation, idempotency, approvals, rate limits, circuit breakers, timeouts that cancel, compensation, audit log
    5. 
    

    

      

        
Direct tool calls

        4 tool calls, 5 model turns
        
    
          
  • A retried call refunds the customer twice
    • 
          
  • A failed step leaves half-done work for the model to undo
    • 
          
  • The model chooses the refund amount
    • 
          
  • The agent holds every API key
    • 
        

      

      

        
Through a Cameleer route

        1 tool call, 2 model turns
        
    
          
  • Each request runs once; a repeat gets duplicate
    • 
          
  • A saga cancels the refund when a later step fails
    • 
          
  • The amount comes from the order, not the prompt
    • 
          
  • Keys stay in the route; every call lands in the audit log
    •

Tools for AI agents

        
Give an agent tools it can call safely across databases, queues, SaaS APIs and files, over MCP or REST: schema validation, idempotency, retries, compensation and an audit log on every call, and a person in the loop for the risky ones.

      

      

        
        
Serverless without the cold start

        
Start per request, scale to zero, pay for milliseconds. No JVM warmup, no snapshot tricks, and the binary is its own AWS Lambda runtime. Build only the components a function uses.

      

      

        
        
Gateways at the edge

        
Run MQTT, syslog and HTTP routing on small devices, filter and aggregate on site, and buffer when the uplink is down, with one binary and no runtime to install, down to 5.9 MB with build features.

Start cameleering: your first route in a minute.

    
Use the container, the Rust crates or the CLI. Every example here is a file in the repository, run end to end by the test suite.


    

      
      
      
    


    

      

        
    
          
  1. Save a Camel YAML route as hello-api.camel.yaml
    2. 
          
  2. Run it in the container
    docker run --rm -p 8080:8080 \
  -v "$PWD:/routes:ro" pmsudhi/cameleer \
  run /routes/hello-api.camel.yaml
    3. 
          
  3. Call it
    curl localhost:8080/orders/42
{"id": "42", "status": "shipped"}
    4. 
        

        

          
hello-api.camel.yaml


- rest:
    path: /orders
    get:
      - path: /{id}
        to: direct:getOrder
- route:
    from:
      uri: direct:getOrder
      steps:
        - setBody:
            simple: '{"id": "${header.id}", "status": "shipped"}'

        

      

      
One native binary on distroless, for linux/amd64 and linux/arm64, non-root and fine with --read-only. On Docker Hub and as ghcr.io/pmsudhi/cameleer. Routes written for Apache Camel's YAML DSL run unchanged. Kubernetes and Cloud Run: deployment guide.

    


    

      

        
    
          
  1. Add the crates to Cargo.toml
    [dependencies]
cameleer-core = "0.4"
cameleer-http = "0.4"
    2. 
          
  2. Write routes in the Rust DSL (right)
    3. 
          
  3. Run and call it
    cargo run --release
curl localhost:8080/api/greet/Ada
    4. 
        

        

          
src/main.rs


use cameleer_core::prelude::*;
use cameleer_http::rest::RestDslExt;

fn main() -> Result<()> {
    let ctx = CamelContext::new();
    cameleer_http::register(&ctx);
    ctx.properties().set("camel.server.port", "8080");
    ctx.add_routes(|b| {
        b.rest("/api/greet").get("/{name}").to("direct:greet");
        b.from("direct:greet")
            .set_body(simple(r#"{"greeting": "Hello, ${header.name}!"}"#));
    })?;
    ctx.start()?;
    loop { std::thread::park(); }
}

        

      

      
To run YAML routes with every component from your own binary, depend on cameleer-main and call cameleer_main::new_main() (embed_yaml.rs).

    


    

      

        
    
          
  1. Install the CLI from crates.io
    cargo install cameleer-main
    2. 
          
  2. Run any Camel YAML route
    cameleer run hello-api.camel.yaml
    3. 
          
  3. Manage running integrations, Camel JBang style
    cameleer ps
cameleer stop hello-api
    4.

Real use cases, ready to run

    
    
      
  • AI ticket triageKafka in. An LLM classifies each ticket P1 or P3, and urgent tickets go to their own topic. OpenAI or any compatible server: Ollama, vLLM, Azure OpenAI.
    • 
      
  • Alerts to SlackAn HTTP webhook takes monitoring alerts, keeps the critical ones and posts them to a Slack channel.
    • 
      
  • Files to S3Watches a folder, uploads each new CSV file to an S3 bucket, then moves it to .done.
    • 
      
  • REST APIJSON endpoints with validation, a content-based router and error handling. Needs nothing else.

      The AI ticket triage route

- route:
    id: ticket-triage
    from:
      uri: "kafka:support-tickets?brokers={{env:KAFKA_BROKERS:localhost:9092}}&groupId=triage&autoOffsetReset=earliest"
      steps:
        - setProperty:
            name: ticket
            simple: "${body}"
        - to: "openai:chat-completion?model={{env:OPENAI_MODEL:gpt-4o-mini}}&baseUrl={{env:OPENAI_BASE_URL:https://api.openai.com/v1}}&temperature=0&systemMessage=Classify the support ticket. Reply P1 for outages, data loss or security issues, otherwise P3. Reply with P1 or P3 only."
        - setHeader:
            name: priority
            simple: "${body}"
        - setBody:
            simple: "${exchangeProperty.ticket}"
        - choice:
            when:
              - simple: "${header.priority} contains 'P1'"
                steps:
                  - to: "kafka:tickets-urgent?brokers={{env:KAFKA_BROKERS:localhost:9092}}"
            otherwise:
              steps:
                - to: "kafka:tickets-routine?brokers={{env:KAFKA_BROKERS:localhost:9092}}"
