Mirth Connect alternatives: the open-source forks, the commercial engines, and interfaces as code

From version 4.6, Mirth Connect is sold only under a commercial, closed-source licence. If your interfaces ran on the open-source edition, you can stay on 4.5.2, buy a licence, move to an open-source fork, move to another commercial engine, or rewrite the interfaces as code. Here is what each option is, with every fact linked to its source.

Cameleer is one of the options on this page, so read it as a vendor's comparison. Each fact about another product is cited to that product's own page or repository, and numbered links go to the sources at the end. Corrections are welcome as a GitHub issue.

What changed with Mirth Connect 4.6

  • On 19 March 2025 NextGen Healthcare announced a move from a dual licence (open source and commercial) to a single commercial, proprietary licence, starting with Mirth Connect 4.6 [1].
  • NextGen's downloads page says the source code for new releases is no longer public, and that upgrading to 4.6 or later needs a licence. It lists Enterprise, Gold and Platinum tiers, with no prices [2].
  • NextGen gave open-source users three choices: stay on their current version, upgrade to 4.5.2 (the last open-source release), or buy a licence and upgrade to 4.6 [1]. The last tagged release in the public repository is 4.5.2, from 23 September 2024 [3].
  • There is a free "Mirth Connect for Research" licence for approved research studies affiliated with a non-profit institution [1].

How to choose

Stay close to Mirth

If your team lives in the Mirth Administrator and has many channels with JavaScript transformers, the least work is to stay on Mirth's code base: a licence for 4.6+, or one of the forks, which both start from the 4.5.2 code [4][6]. Check each fork's notes for how it handles your channels, plugins and Java version before you move.

Move to interfaces as code

If you would rather review interfaces in pull requests, test them in CI and deploy them like any other service, a framework fits better: Apache Camel on the JVM, or Cameleer as one native binary. The cost is a rewrite: there is no channel importer, and Mirth's JavaScript transformers do not run.

Where Cameleer fits, and where it does not

A good fit when

  • you want an Apache-2.0 engine whose licence will not change under you;
  • you want interfaces reviewed, tested and deployed as code;
  • the engine must be small: one native binary, no JVM and no database, for a gateway or a container;
  • you need HL7, FHIR and DICOM in one engine, alongside Kafka, databases, cloud services or AI tools.

Not a fit (yet) when

  • your team needs a visual channel editor or a message browser;
  • you want to import Mirth channels or keep their JavaScript;
  • you need cloud healthcare services tested today (Azure, Google, AWS), or Storage Commitment, MPPS and pixel transcoding for DICOM;
  • you need throughput figures against Mirth before you choose: none have been measured yet.

Common questions

Is Mirth Connect still open source?

Not from version 4.6. NextGen moved to a single commercial, proprietary licence with 4.6 (announced on 19 March 2025), and the source code for new releases is no longer public. Version 4.5.2 is the last open-source release.

What are the open-source alternatives to Mirth Connect?

Two forks of Mirth's code: Open Integration Engine (MPL-2.0, community governed, an incubating Eclipse project) and BridgeLink (MPL-2.0 server, from Innovar Healthcare, with paid plugins and support available). Outside Mirth's code base, Apache Camel (Java) and Cameleer (Rust, with the health pack) are Apache-2.0 frameworks for interfaces as code.

Can I keep using Mirth Connect 4.5.2?

NextGen listed staying on the current version or upgrading to 4.5.2 as options for open-source users. New releases from 4.6 need a licence.

Which commercial engines replace Mirth Connect?

Rhapsody, Infor Cloverleaf, InterSystems Health Connect and Qvera Interface Engine are healthcare integration engines sold by their vendors; each vendor's page lists HL7 v2 and FHIR, and some list DICOM and X12.

Can Cameleer import Mirth channels?

No. Channels are rewritten as Apache Camel YAML routes: an MLLP listener becomes from: mllp:..., destinations become endpoints, filters and transformers become steps. Mirth's JavaScript transformers do not run.
