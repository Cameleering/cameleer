Known losses and limits

  • p99 latency for HTTP into Kafka is higher than Camel on the JVM (8.6 ms against 7.8 ms) while serving 1.7 times the requests: Cameleer batches concurrent sends.
  • Load model: the comparison with Apache Camel uses a closed-loop driver, the same on both sides: N workers each send the next request when the last is answered. Throughput is what each side sustains at saturation, and p99 is the latency at that saturation, timed from when each request was sent, so it is not corrected for coordinated omission. Read the p99 rows as relative (BENCHMARKS).
  • Plain HTTP is the smallest throughput gain: a fixed-reply route reaches 1.7x Camel's throughput but 68% of a do-nothing server on the same machines (the HTTP ceiling). simoom is the project meant to close that gap.

Method, every scenario and the raw data: BENCHMARKS and how we tested; raw results in benchmarks/results/2026-11-06-linux, generated by scripts/cloud-bench/summarize.py.

Known losses and limits

  • Load model: simoom’s request-rate and latency tests are open-loop (a constant rate, each request timed from when it was due) and its overload test offers a fixed absolute rate. Its TLS handshake, HTTP/3 and bulk-download tests are closed-loop, so those figures are throughput at saturation.
  • Under overload simoom answers about as many requests in total as the others (150.3k, against 150k–160k for most servers), but few of them within 1 ms: actix-web answered 59.0k in time and nginx 29k.
  • A new connection per request: 5th of 19. xitca-web is 29% ahead, cameleer-http 9%, actix-web 5% and may-minihttp 4%.
  • The 64-connection plaintext row is a single round in which simoom stalled, so it is not a fair reading of simoom's throughput at that load.
  • The degraded-network result from campaign 3 (2026-11-11: may-minihttp kept 114.7k req/s while simoom and the others fell to 17k–62k) was not retested.
  • Larger machines and multi-queue NICs are not measured yet.

How the ledger works

What a row needs

  • A named baseline with its exact version: the software people run today.
  • Both sides on the same hardware, with the machine type written down.
  • A script anyone can rerun, and the raw results.
  • Both ends of every range: "4.8–54x", never only "54x".
  • The losses, in the same table as the wins.

How rows change

  • Cameleered rows carry numbers: measured against a named current baseline on the same hardware, with a rerunnable script, losses disclosed, within 12 months (the labels). Cameleering rows are in progress and show targets only; planned rows are not started. Neither carries numbers.
  • A target is shown hollow, like 10x, and never in the result column.
  • A result older than 12 months is marked stale until it is rerun.
  • Rows are never deleted. A newer run supersedes an old one, which stays visible, struck through.

Measured your own software the same way? The method has the report format.
